## 2. Что неоднозначно

### N-1. Поведение `surface()` с повреждёнными ластами и на суше

В разд. 3.4.3 сказано: «Устанавливает `depth_m = 0`. Энергию не тратит. Если тюлень уже на поверхности, ничего не меняется». Раздела «Исключения» у метода нет. В разд. 2 сказано: «Если ласты повреждены, тюлень не может двигаться ни по воде, ни по суше».

Проблема: не определено, можно ли всплыть с повреждёнными ластами. Если нельзя, тюлень на глубине «застревает», потому что `move` и `dive` выбрасывают `JetSealNoFins`. Также не сказано, считается ли «на поверхности» тюлень, который находится на суше (`is_swimming == False`, `depth_m == 0`).

Предлагаю: явно записать в 3.4.3, что `surface()` не выбрасывает исключений, работает при повреждённых ластах и на суше ничего не меняет. Добавить TC: всплытие с глубины 10 после `damage_fins()` даёт `depth_m == 0`; `surface()` на берегу не меняет состояние.

### N-2. Проверка типов в `dive`, `refuel`, `can_overcome`

В разд. 3.2 и 3.4.1 указан `TypeError` для «не числа» и «не строки». В разд. 3.4.2, 3.4.4 и 3.4.6 в списке исключений есть только `ValueError`.

Проблема: не определено, что вернут `dive("5")`, `refuel(None)`, `can_overcome(42)`. Также не сказано, считается ли числом `bool`: `JetSeal("Плюх", True, 1.2, 40)` и `move(True, "water")` формально проходят проверку, потому что `bool` — подкласс `int`.

Предлагаю: ввести общее правило для всех методов («число — `int` или `float`, но не `bool`; иначе `TypeError`») и добавить в TC-04, TC-15, TC-24, TC-29 входы неверного типа.

## 3. Что не покрыто тестами

### P-1. Порядок проверок проверен только для одной пары

В разд. 3.4.1 задан порядок «distance_km → terrain → воздух → ласты → энергия», в разд. 3.4.2 — «depth_m → ласты → поверхность → глубина → энергия». В TCS порядок проверяет только TC-09: случай `move(-1, "air")`.

Проблема: остальные пары из объявленных порядков не проверяются. Например:
- `move(1, "air")` при повреждённых ластах → должно быть `JetSealCannotFly`;
- `move(1, "water")` при повреждённых ластах и `energy = 0` → `JetSealNoFins`;
- `dive(5)` на берегу при повреждённых ластах → `JetSealNoFins` (TC-16 проверяет только тюленя в воде);
- `dive(15)` при `fin_length_m = 0.5` и `energy = 2` → `JetSealTooDeep`, а не `JetSealNoStrength`;
- `dive(0)` на берегу → `ValueError`.

Также не указано, где в порядке стоит `TypeError`: что вернёт `move("abc", "lava")`?

Предлагаю: добавить TC «порядок проверок» для `move` и `dive` с перечисленными входами и вписать `TypeError` первым шагом порядка в 3.4.1.

### P-2. Ровно хватающая энергия при погружении

В разд. 3.4.1 сказано: «Энергии ровно хватает (затраты == energy): движение разрешено, energy = 0». Для `dive` в разд. 3.4.2 такого правила нет. В разд. 5 и TCS граница проверена только для `move` (TC-12).

Проблема: неясно, разрешено ли `dive(10)` при `energy = 5` (затраты 5 == energy). Тест на это отсутствует.

Предлагаю: дописать правило в 3.4.2 и добавить TC: `energy = 5`, `dive(10)` → `depth_m == 10`, `energy == 0`.

## 4. Что противоречиво

### K-1. Повреждённые ласты и препятствия «reef», «dam»

В разд. 2 сказано: «Если ласты повреждены (`fins_intact == False`), тюлень не может двигаться ни по воде, ни по суше». В разд. 3.4.4 условие `fins_intact` есть только у `"whirlpool"`. Для `"reef"` условие — `depth_m > 0`, для `"dam"` — `is_swimming == False`.

Проблема: на берегу после `damage_fins()` метод `can_overcome("dam")` вернёт `True` («перебирается по суше»), но `move(1, "ground")` выбросит `JetSealNoFins`. То же для рифа на глубине. Препятствие «преодолимо», хотя двигаться тюлень не может.

Предлагаю: добавить `fins_intact` в условия `"reef"` и `"dam"` и расширить TC-22, TC-23 случаем с повреждёнными ластами. Если такое поведение задумано, объяснить в 3.4.4, почему `whirlpool` проверяет ласты, а остальные нет.

### K-2. Атомарность `dive` есть в TCS, но не в SPEC

В разд. 3.4.1 для `move` сказано: «При любом исключении состояние не меняется». В разд. 3.4.2 для `dive` такой фразы нет. При этом TC-18 ожидает «JetSealTooDeep (состояние не меняется)», а TC-19 — «depth=0; energy=2».

Проблема: тесты требуют поведения, которого нет в нормативном тексте ТЗ. Разработчик, читающий только SPEC, может, например, списать энергию до проверки глубины.

Предлагаю: добавить в 3.4.2 фразу «При любом исключении состояние не меняется» (или вынести её общим правилом для всех методов).
