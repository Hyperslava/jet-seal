### N-1. Поведение `surface()` с повреждёнными ластами и на суше

**Решение:** принято.

**Обоснование:** замечание верно: в 3.4.3 не было сказано, можно ли всплыть с повреждёнными ластами и что происходит на суше. Без такого правила тюлень, у которого ласты повредились на глубине, «застревал» бы, потому что `move` и `dive` выбрасывают `JetSealNoFins`. Всплытие — пассивное действие и энергии не требует, поэтому от состояния ласт не зависит.

**Что изменено:**
- SPEC 3.4.3: `surface()` не выбрасывает исключений, работает при повреждённых ластах; на суше (`is_swimming == False`, `depth_m == 0`) состояние не меняется.
- TCS: TC-20 расширен тремя входами (на глубине дважды; на глубине с повреждёнными ластами; на берегу).

### N-2. Проверка типов в `dive`, `refuel`, `can_overcome`

**Решение:** принято.

**Обоснование:** в ТЗ `TypeError` был описан только для конструктора и `move`, а для остальных методов поведение при неверном типе не определено. Замечание про `bool` тоже верно: `True` формально подкласс `int`, но числом в предметной области не является.

**Что изменено:**
- SPEC: добавлен раздел 3.5 «Общие правила»: число — это `int` или `float`, но не `bool`; строка — `str`; иначе `TypeError`. Правило действует для конструктора и всех методов.
- SPEC 3.4.2, 3.4.4, 3.4.6: в списки исключений добавлен `TypeError`.
- TCS: TC-04 (`bool` и `None` в числовых параметрах), TC-15 (`dive("5")`, `True`, `None`), TC-24 (`can_overcome(42)`), TC-29 (`refuel(None)`, `"5"`, `True`).

### P-1. Порядок проверок проверен только для одной пары

**Решение:** принято.

**Обоснование:** в ТЗ объявлен порядок проверок для `move` и `dive`, но тестировалась только одна пара. Без остальных пар разработчик мог бы реализовать другой порядок, и тесты этого не заметили бы. Новых тест-кейсов для этого не добавлено: каждая пара проверяется как дополнительный `subTest` в тесте, который уже проверяет соответствующее исключение, чтобы не дробить TCS.

**Что изменено:**
- SPEC 3.4.1, 3.4.2, 3.5: порядок проверок записан явно, первым шагом идёт проверка типов (`TypeError`). `move("abc", "lava")` даёт `TypeError`.
- TCS и тесты: `move(1,"air")` при повреждённых ластах (TC-08); `move` при повреждённых ластах и `energy = 0` (TC-11); `dive(5)` на берегу при повреждённых ластах (TC-16); `dive(15)` при `fin_length_m = 0.5` и `energy = 2` (TC-18); `dive(0)` на берегу (TC-15); `move("abc","lava")`, `move(True,"water")`, `move(1, 5)` (TC-09).

### N-1. Числовые значения NaN и бесконечность

**Решение:** принято.

**Обоснование:** замечание верно: `float("nan")` проходит проверку типа, а сравнения `<= 0` и `> 100` с ним дают `False`, поэтому разные реализации по-разному обрабатывали бы `move(float("nan"), "water")`; `+inf` удовлетворяет условию `> 0`. Выбрано простое и проверяемое правило: допустимы только конечные числа, NaN и ±inf отклоняются.

**Что изменено:**
- SPEC 3.5: числовой аргумент должен быть конечным; проверка конечности идёт после проверки типа и до проверки диапазона.
- SPEC 3.2, 3.4.1, 3.4.2, 3.4.6: в списки исключений добавлен `ValueError` для NaN и ±inf.
- SPEC 6.2: сообщение «<параметр> must be finite».
- TCS и тесты: TC-02, TC-03, TC-09, TC-15, TC-26, TC-29 расширены входами NaN и ±inf; для методов, меняющих состояние, проверена неизменность состояния после отказа.

### N-2. Владение словарём `get_status`

**Решение:** принято.

**Обоснование:** для вызывающего «копия» и «живой словарь» — разные контракты, а в ТЗ ничего не сказано. Выбран снимок: он безопаснее для вызывающего и соответствует названию метода.

**Что изменено:**
- SPEC 3.4.8: каждый вызов возвращает новый независимый словарь; изменение словаря не меняет тюленя, а последующие действия тюленя не меняют ранее полученный словарь.
- TCS и тесты: TC-31 расширен проверкой обеих сторон независимости.

### P-1. Доступ только для чтения не проверяется

**Решение:** принято.

**Обоснование:** в SPEC 3.3 атрибуты объявлены доступными только для чтения, но ни одного теста на запрещённое присваивание не было. Реализация с обычными изменяемыми полями прошла бы все тесты, хотя вызывающий смог бы выполнить `seal.energy = -100` или `seal.fins_intact = True` без ремонта.

**Что изменено:**
- SPEC 3.3: присваивание любому из десяти публичных атрибутов вызывает `AttributeError`, значение атрибута не меняется.
- TCS и тесты: новый TC-37 с `subTest` по всем десяти атрибутам. Сделан отдельным тест-кейсом, а не расширением TC-05, потому что это самостоятельное правило ТЗ.
- SPEC 8: добавлена строка трассируемости.

### P-2. Строгая граница длины ласт для водоворота

**Решение:** принято.

**Обоснование:** правило `fin_length_m > 1.0` строгое: при ровно 1.0 м результат `False`. Тесты же проверяли только длины 1.2 и 0.6 м и границу не затрагивали, поэтому ошибочная реализация с условием `>= 1.0` прошла бы все тесты.

**Что изменено:**
- TCS и тесты: TC-21 расширен случаями `fin_length_m = 1.0` → `False` и `1.001` → `True` (в воде, ласты целы).
- SPEC 5: добавлен граничный случай. Само правило не менялось.

### K-1. Заявленная проверка сообщения о нехватке энергии слабее контракта

**Решение:** принято.

**Обоснование:** замечание верно: SPEC 6.2 задаёт формат `not enough energy: required X, have Y`, а TC-10 и TC-19 проверяли только префикс, так что строка `not enough energy: wrong calculation` прошла бы проверку. Выбран вариант «числа входят в контракт»: требуемая и доступная энергия — полезная диагностическая информация, а проверка чисел несложна. Вариант с ослаблением формулировки SPEC отклонён.

**Что изменено:**
- SPEC 6.2: X и Y — требуемая и доступная энергия в десятичной записи; целое значение можно записывать как с `.0`, так и без него (`20` и `20.0`).
- Тесты: TC-10 проверяет числа 20 и 10, TC-19 — числа 5 и 2.
- SPEC 8: строка трассируемости для формата сообщения.
